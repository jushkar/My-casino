# Official compatibility review — 2026-11-15 UTC

These are documentation findings, not hosted observations or live Auth results. Supabase's documentation connector and public web search were accessible. The execution environment's single request for `https://supabase.com/changelog.md` failed with curl 56, proxy CONNECT 403 and HTTP 000; the public web tool could read the index and linked notices. Neither surface establishes runtime access to the development project.

| [Sessions](https://supabase.com/docs/guides/auth/sessions) | Five-minute JWTs are within the documented range; shorter values are discouraged. Rotation has reuse-window and parent-token exceptions, so it is not universal introspection. Outstanding access tokens can remain valid after sign-out. Application wall-clock idle/absolute limits remain independent. Current project TTL, reuse interval and actual refresh behavior are NOT VERIFIED. Provider-native session limits may require a paid plan; no paid option is selected or needed for the proposed application timer. |
| [JWT fields](https://supabase.com/docs/guides/auth/jwt-fields) | Password/TOTP AMR entries and timestamps, AAL, session ID, issuer, audience, iat and exp are documented claims. The docs do not prove this project's timestamps stay stable through refresh/MFA. Missing or changed required claims must deny access, not reset application lifetime. |
| [getUser](https://supabase.com/docs/reference/javascript/auth-getuser), [getClaims](https://supabase.com/docs/reference/javascript/auth-getclaims) | getUser contacts Auth; getClaims verifies the JWT, using cached JWKS for asymmetric signing or Auth for symmetric signing. Neither documentation establishes universal immediate external session revocation. Keep both online identity and verified-claims gates. No getSession user object is authorization authority. Actual signing configuration is NOT VERIFIED. |
| [MFA](https://supabase.com/docs/guides/auth/auth-mfa), [TOTP](https://supabase.com/docs/guides/auth/auth-mfa/totp), [challengeAndVerify](https://supabase.com/docs/reference/javascript/auth-mfa-challengeandverify) | Password entry followed by TOTP challenge/verification is supported. Signed AAL2 and recent TOTP must be checked in the BFF and database. Factor removal can leave stale AAL until refresh. Test returned tokens, AMR freshness, factor removal, and attempted MFA token reissuance after external logout before accepting a revocation bound. No enrollment or live challenge was performed. |
| [Roles](https://supabase.com/docs/guides/database/postgres/roles), [superuser limitations](https://supabase.com/docs/guides/database/postgres/roles-superuser) | Separate service database roles are supported in principle. Supabase customer access is not unrestricted superuser access. Documentation does not prove the actual migrator's CREATEROLE, membership transfer, event-trigger permissions or effective privileges. Do not grant the gateway to authenticator/authenticated or give it inherited/bypass privileges. |
| [Database functions](https://supabase.com/docs/guides/database/functions), [RLS](https://supabase.com/docs/guides/database/postgres/row-level-security) | Fixed search_path, revocation of default function EXECUTE, independent authorization and narrow ownership are essential. SECURITY DEFINER executes as its owner; it does not inherently bypass RLS when the owner lacks table ownership/BYPASSRLS and memberships. The RLS guide cautions against exposed definer functions. ADR-003's one public definer RPC is a deliberate exception requiring security review: it has explicit grants, permit/user checks, and a non-table-owning executor. No hosted compatibility approval is inferred. |
| [Database connections](https://supabase.com/docs/guides/database/connecting-to-postgres) | Direct connections suit persistent IPv6 servers; shared session pooling supports IPv4 and custom-role usernames. Copy the actual pooler endpoint from the authorized Connect dialog; region does not uniquely determine it. Use verified TLS/CA and the dedicated role only. Transaction pooling has session-state/prepared-statement constraints. Prefer direct/session mode for initial validation; hosted endpoint, TLS, login and session_user behavior remain NOT VERIFIED. |

## Explicit architecture qualifications

The gateway is a trusted BFF attestor. Its SQL accepts claim JSON to create pending session/permit state for the existing binding; SQL does not verify a JWT signature there. It cannot create a new binding or Supabase identity, and a gateway credential alone cannot run owner data actions. Independent PostgREST verification of the matching owner JWT remains necessary. A stolen gateway credential plus a matching valid owner JWT could bypass the intended online BFF verification path, and gateway-only compromise can forge pending-session audit entries or cause denial of service. New SQL case 29 demonstrates the accepted-claims versus denied-action boundary; it is not a hosted forgery test. Treat credential custody and this trust assumption as explicit review items.

No architecture change, runtime relaxation or migration edit was made. Hosted default ACLs/exposed schemas/roles may differ from the isolated fixture. The exact existing migration must remain blocked until those facts and all live acceptance tests are established. Neither metadata access nor a healthy project status validates its applicability.
