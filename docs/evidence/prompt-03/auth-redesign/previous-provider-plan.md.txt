## Exact proposed change

Review [`20261113231743_staff_foundation.sql`](../../../supabase/migrations/20261113231743_staff_foundation.sql) and [security review](sql-review/README.md). It changes only the draft staff foundation, without wallet configuration. Objects:

- New NOLOGIN/NOINHERIT/NOBYPASSRLS function-owner role `mc_staff_executor`, with no membership in either direction and no owned tables. Its temporary schema CREATE rights are revoked before commit. Ambient PUBLIC CREATE, extra Auth column rights, table ownership or role membership cause the migration to abort.
- Private schema `mc_staff_private`, tables `roles`, `sessions`, `records`, `audit`, constraints and scoped executor RLS policies. ENABLE and FORCE RLS apply to all four tables. Tables remain owned by the migration administrator, separately from the function owner. UUID defaults require no sequence grants. Runtime roles cannot write roles, delete sessions, update/delete records, or edit audit rows. There is no public staff elevation path.
- `roles` is authoritative on every gate; neither app nor user JWT metadata grants staff status. Only active `wallet_admin` at AAL2 is permitted. Records are now private to the staff author, including SELECT RLS; audit inserts bind actor and record owner to `auth.uid()`.
- Private `gate()` and public `staff_gate()`, `staff_records_list()`, `staff_record_create(text)` functions, SECURITY DEFINER with empty search path and explicit object references. Default PUBLIC EXECUTE is revoked transactionally for every function; authenticated gets only the three public RPCs. Future functions still require explicit ACL review; this migration deliberately does not change unrelated global default privileges.
- **High-risk managed Auth dependency:** column SELECT `(id,user_id,created_at,not_after)` and two SELECT policies on `auth.sessions`: scoped permissive `mc_staff_current_session` and restrictive `mc_staff_session_scope`. The restrictive policy prevents another permissive PUBLIC policy from broadening executor row scope. No existing Auth policy is changed or removed by the forward migration. The application role does not own the Auth table or bypass its RLS.

## Session semantics

Absolute lifetime is eight hours from Auth `created_at`, regardless of staff use. The first eligible staff request inside that lifetime initializes `first_seen` and `last_seen` from database wall time. Ordinary Auth use before that first request does not consume staff idle time. After first use, 30 minutes without a successful authorization expires that staff session permanently; requests denied for idle, role, AAL, revoked/missing session, expired claims or invalid input do not revive it. A new Auth login/session ID is required after expiry. Refreshing tokens under the same session ID cannot reset it. Successful authorization/page reads count as activity, not just writes. Invalid POST note input is rejected before the BFF gate and by the SQL mutation before the SQL gate.

The session PK and row lock serialize parallel first-use/activity requests. Wall time is re-read after locking and current role/session visibility is checked again. Claims must include authenticated role, valid session UUID, unexpired numeric `exp` and AAL2. `not_after`, when present, is enforced as an additional upper bound. READ COMMITTED is required; stale snapshot transaction modes are denied. A committed row deletion causes subsequent requests to deny; a deletion race at first-use FK insertion returns unauthenticated and rolls back gate changes. Already-authorized in-flight operations are not canceled by a later logout. No claim of stronger cross-service linearizability is made.

## Managed-schema decision and remaining blockers

[Supabase sessions documentation](https://supabase.com/docs/guides/auth/sessions) documents correlating JWT `session_id` with `auth.sessions` and checking row existence for logout. It also says sessions can remain in the database after configured timeout and that access tokens may remain valid until expiry. [Supabase managed-schema guidance](https://supabase.com/docs/guides/database/prisma/prisma-troubleshooting#drift-detected-your-database-schema-is-not-in-sync-with-your-migration-history) warns that managed schemas change with platform updates. These sources do **not** establish a compatibility guarantee or permission for customer policies and grants on Auth tables.

Real PostgreSQL tests prove the ACL/policy approach works with the fixture, and that CREATEROLE alone cannot create a policy on another role's managed table. The fixture Auth table is owned by `supabase_auth_admin` and has RLS enabled; migration execution used an isolated PostgreSQL superuser. The actual hosted migration runner, table owners, existing policies, column ACLs, members and default privileges have **not** been inspected during this task. Hosted `postgres` is not assumed to be a superuser; temporary ADMIN/membership created by CREATEROLE may also fail this draft's zero-membership check. Do not work around those failures by granting broad runtime access or BYPASSRLS. Owner/provider approval and a supported provisioning route are prerequisites.

No supported alternative meeting immediate external revocation has been established. `getUser()`/JWT verification, shorter token TTL alone, and a BFF-only blacklist cannot prove arbitrary provider logout/revocation immediately. A postgres/Auth-owner definer bridge or BYPASSRLS role would widen the approved privilege boundary. The narrowly scoped managed-table design remains a blocked proposal, rather than weakening the revocation requirement. Full provider inactivity, refresh revocation and upgrade behavior remain unverified even with `not_after` and JWT expiry checks.
