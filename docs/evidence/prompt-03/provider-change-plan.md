## Exact proposed objects and grants

- Create application role `mc_staff_executor` NOLOGIN, NOINHERIT, NOSUPERUSER, NOCREATEDB, NOCREATEROLE, NOREPLICATION, NOBYPASSRLS. It owns the eight functions below and no relations.
- Create private schema `mc_staff_private`, owned by the trusted migrator, outside the exposed API schemas. No public/anon/authenticated/service-role USAGE or table privileges. Executor gets only USAGE after creation completes.
- `roles`: `user_id` UUID primary key, constrained `wallet_admin` role, active flag default false, creation timestamp. Executor SELECT only; no runtime role mutation. No user-editable metadata authority.
- `sessions`: provider session UUID primary key, user UUID, SHA-256 capability hash, authentication/expiry/creation timestamps and optional revocation timestamp. Check: expiry cannot exceed authentication + five minutes. Executor SELECT, INSERT and UPDATE(revoked_at) only; no DELETE, capability replacement or extension.
- `records`: UUID key, bounded printable nonmonetary note, authenticated creator, DB timestamp. Executor SELECT/INSERT only; author-private records.
- `audit`: UUID key, actor, constrained action (`session.open`, `session.close`, `record.create`), session and optional record reference, DB timestamp. Executor INSERT only. No runtime read/update/delete. Audit failure rolls back the operation. UUID defaults require no sequences.
- Private helpers `claims()`, `identity(boolean)`, `gate(text)`. Claims reads verified PostgREST request context instead of calling a managed Auth helper. Not exposed/executable by public API roles.
- Public authenticated-only RPCs: `staff_session_open(text)`, `staff_session_close()`, `staff_gate(text)`, `staff_records_list(text)`, `staff_record_create(text,text)`. No overloads or other public RPCs are created. These are callable directly and contain their own authorization checks; see the explicit direct-call limitation in ADR-002.
- Four application tables have ENABLE and FORCE RLS. Seven policies scope role/session/record/audit access to the current verified user, session and record owner. No `USING(true)` policy or blanket schema/table/function grant.
- Every function has empty search_path; definer functions use qualified relation names, built-ins resolve from pg_catalog. PUBLIC/anon/authenticated/service_role execution is explicitly revoked for every new function, then authenticated gets only the five public RPCs. Global default privileges on unrelated future functions are not changed; future migrations must revoke default PUBLIC execution themselves.
- **No changes or runtime references to managed Auth tables, including auth.sessions or auth.users.** No managed foreign keys, owner bridge, grants, policies or BYPASSRLS executor. Identity UUIDs remain in app history after provider deletion; retention/reconciliation is a separate controlled operation.

## Ownership and migration runner boundary

The transaction checks for any existing executor role, private schema, or public RPC name and aborts on conflict. It never reuses/replaces existing objects or data. CREATE privileges granted to the executor for function ownership transfer are revoked before commit.

A non-superuser CREATEROLE migrator needs temporary SET/INHERIT membership to transfer ownership and revoke function ACLs after transfer. The transaction grants this membership only to its current trusted migrator, then revokes it. PostgreSQL 17 may retain the automatically bootstrap-granted **ADMIN-only** membership for the role creator, with both SET and INHERIT false. The final assertion allows exactly this trusted current-user membership and rejects runtime memberships, executor memberships in other roles, executor-owned tables or effective schema CREATE. ADMIN can deliberately regrant privileges; the migrator is trusted and already owns app tables, so this is not a boundary against a compromised migration administrator. Runtime credentials must never be that administrator.

Real isolated tests used PostgreSQL 17.12 and non-superuser `mc_migrator` with CREATEROLE and application schema/database creation rights. Membership syntax/catalog fields require PostgreSQL 16+. Hosted PostgreSQL version, migration role CREATEROLE/CREATE/GRANT rights, ambient PUBLIC privileges, default ACLs, existing memberships and Data API configuration remain unverified. No broad privilege workaround or managed Auth ownership is requested. If the actual runner cannot satisfy these app-only prerequisites, stop and revise the reviewed proposal.

## RLS threat model

PostgREST verifies JWTs before supplying request.jwt.claims; SQL does not independently verify signatures. Never issue raw authenticated/executor SQL login credentials or expose a generic SQL function that can set trusted claim settings. RLS author/session predicates narrow the executor's table access; function checks enforce current staff role, AAL2, token expiry, password freshness and capability. Table owners ordinarily bypass RLS unless FORCE applies; superusers and BYPASSRLS still bypass FORCE. This executor owns functions only and cannot inherit/SET an owning/bypass role. SQL tests exercised the actual function-owner/RLS combination, not only text patterns.

Direct authenticated RPC invocation must not bypass role/MFA/expiry/tombstone checks. It can bypass the BFF's online getUser, cookie/CSRF and IP middleware because it uses explicit bearer authentication. ADR-002 documents the residual during external logout/Auth-only outage and requires approval. App-local revocation is atomic, durable and tested. External provider state is not inferred from app state. A stolen active JWT/capability can be replayed before revocation/expiry; a direct valid staff JWT can choose a capability. No claim of bearer-token theft prevention or global immediate provider revocation is made.

## Deployment assumptions — disabled, unverified

Serve Vite public assets and the BFF behind one HTTPS origin. Route `/staff`, `/staff/*`, `/api/*` to the BFF and preserve exact Origin and cookie headers. No staff response caching, CORS reflection, alternate origins, redirect forwarding or public BFF listen address. TLS termination/proxy chain and Safari behavior require tests; localhost inject tests do not prove them. Every auth/capability cookie: Secure, HttpOnly, Path=/, no Domain, SameSite=Lax; CSRF bootstrap cookie is Strict. Cookie lifetime is not the authorization lifetime. Session/CSRF secrets remain outside VITE variables and bundles.

Fastify currently binds loopback, uses `trustProxy:false`, and trusts only the immediate peer IP. Behind a proxy this collapses clients into that IP; it does not safely establish client identity. Before multi-instance use, supply a reviewed trusted-proxy CIDR/hop topology and shared atomic rate-limit store (or equivalent edge limits), with account/IP abuse controls. Never enable blanket forwarded-header trust. Registry state is shared in PostgreSQL; CSRF signing secret must be shared securely across instances; per-process rate limits are not globally enforced. Direct bearer RPCs also require provider-side abuse limits. Clock synchronization and request/statement timeouts need verification. No public activation is permitted on the strength of local tests.
